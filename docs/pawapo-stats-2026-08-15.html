03

日々どう使われているか

セッションの63%が平日日中の9時から17時台に集中し、ピークは14時台。業務時間内に使われる道具として定着していることが、時間帯・曜日の両方から読み取れます。

時間帯と曜日

公開版の全セッションを日本時間の時間帯で割ると、9時から17時台が全体の63%を占めます。最も多いのは14時台、次いで9時台。深夜0時から5時台は8%で、業務時間外の利用は限定的です。曜日別では火曜が1日平均22.7回で最多、土曜が12.2回で最少と、平日が週末の1.5倍から1.9倍でした。

「思いついたときに触るツール」ではなく「業務時間内に仕事として使うツール」になっています。資料作成という用途からすれば自然ですが、平日日中に負荷が寄るということは、この時間帯の応答速度と安定性が体験を決めるということでもあります。

04

ユーザーは何を作っているか

実際の依頼文3,078件を分類しました。AI・クラウド技術が約4割を占める一方、同じくらいの割合が一般教養・生活・他分野の業務で、技術者向けツールの枠を越えて使われています。

みのるん自身の利用は、完全には切り分けられません。AgentCore のログにはセッションID（UUID）しか記録されておらず、どのユーザーの依頼かを判別する情報がありません。そこで、明らかな動作確認と自己言及（「テストスライド」「元気？」「みのるんを調べて」など）122件を機械的に除いたうえで集計しています。デモや検証で本番環境を使ったぶんは、この数字に一定量含まれている前提で読んでください。切り分けたい場合の対処は最終セクションに書きました。

05

コスト効率の実像

費用の9割はAIモデルの推論そのものです。インフラは月2ドル未満で、これまでのレポートに載っていた「インフラ数百ドル」は、共有アカウントに同居していた別アプリの費用でした。

実際の内訳（2026年7月）

7月は Project タグでアプリの費用を正確に切り出せる唯一の月です。この月の公開版の全費用は201.35ドルで、内訳は次のとおりでした。

過去レポートの「累計インフラコスト712ドル」は取り下げが必要です。当時は共有アカウント全体の費用をアプリに割り当てていましたが、中身を確認すると Security Hub が月80ドル、EC2 が月50ドル、WAF が月25ドル、SageMaker と、いずれもパワポ作るマンとは無関係の同居アプリの費用でした。タグで正確に切れる7月で見ると、アプリ本体のインフラ費用は月1.79ドルです。このアプリは「サーバーレスでインフラ費用がほぼゼロ、費用はほぼ全額がトークン課金」という構造だと言えます。

単価はどう動いたか

セッション単価は2月から5月にかけて0.58ドルから0.88ドルへ悪化し、6月以降は0.4ドル前後まで改善しました。5月の悪化は、リリースが2か月止まっていた時期に長文・高難度の依頼だけが残ったことが主因と見られます。6月以降の改善は、プロンプトキャッシュの効きと、7月に追加したモデル選択肢の影響が重なったものです。

8月13日に標準モデルを Kimi K2.5 へ切り替えた効果は、まだ測れていません。8月の費用に計上されているのは主に切替前の Sonnet 4.6 分（36.84ドル）で、Kimi の課金は Cost Explorer にまだ現れていません。加えて8月14日に専用アカウントへ移設したため、新環境の費用データはこれからです。Kimi 標準化のコスト効果は、9月に入ってから改めて測るのが確実です。

モデルの変遷

これまでに試したモデルは10種類近くあります。初期の Sonnet 4.5 から始まり、Kimi K2 の採用と撤退、Opus 4.6 と Haiku 4.5 と DeepSeek V3.2 の同時期の試行、2月中旬の Sonnet 一本化、2月17日からの Sonnet 4.6、4月の Opus 4.7 追加、7月の Kimi K2.5 復活と GPT-5.6 Sol 追加、そして8月13日の Kimi K2.5 固定という流れです。現在は Sonnet 4.6・Sonnet 5・GPT-5.6 Sol・GLM-5・Opus 4.6 の設定をコードに残したまま無効化し、Kimi K2.5 だけを有効にしています。

06

記録を残す仕組みの提案

ここまでの数字が取れたのは、旧環境をまだ消していないからです。切り戻し用に残している旧リソースを撤去した瞬間、この記録は二度と再現できません。何が失われかけているかを整理し、そのうえで手当ての案を示します。

データいまの所在保持設定失われる条件
ユーザー 1,076人第1世代のユーザープール 無期限プール削除で即消滅
ユーザー 505人第2世代のユーザープール 無期限プール削除で即消滅
セッションログ 2,799件第1世代のロググループ 無期限ランタイム・ロググループ削除で消滅
セッションログ 920件第2世代のロググループ 無期限同上
セッションログ（新環境）第3世代のロググループ 30日30日経過で自動削除
費用データCost Explorer（4アカウント） 14か月2027年3月ごろ1月分から順次消滅

新環境のログ保持が30日に設定されている点が、いちばん先に手を打つところです。このままだと来月以降は直近30日より前を一切振り返れません。なお AgentCore のロググループはランタイム側が自動で作るもので、CDK では保持期間を管理していません（infra/lib/agent-stack.ts にログの記述はなく、Lambda 側だけ ONE_MONTH を明示）。旧環境を撤去する前に、この文書の数字が保存済みであることを確認してください。

提案：3つの手当てを、この順で

作り込みすぎない構成を勧めます。1と2だけで今回の課題はほぼ解消し、3は生ログが残っていれば急ぎません。

優先やること手間効果
1 ログ保持を30日→400日へput-retention-policy を1本。ランタイムを作り直すとロググループ名が変わるので、デプロイ手順へ組み込む コマンド1本 過去を失わない。生ログさえ残れば、今回と同じ集計をいつでもやり直せる
2 ログにユーザー識別子を出すJWT の sub をハッシュ化した値と、本人フラグをセッション属性へ アプリ側の小改修 みのるん自身の利用を除外できる。加えてリピート率・ヘビーユーザー・1人あたり利用回数が測れるようになる
3 月次集計の自動書き出しEventBridge の月次ルールで Lambda を起動し、前月の集計JSONをS3へ CDKへ追加実装 ロググループが変わっても集計値だけは残る。1をやるなら後回しでよい

おすすめは1と2の組み合わせです。1はコマンド1本で、これをやらないと来月データが消えるので緊急度が高い。2は今回いちばん困った「本人の利用を切り分けられない」に直接効くうえ、ユーザー1人あたりの利用回数という、いま完全に見えていない指標が取れるようになります。保持料金は現在のログ量（新環境で数MB／月）なら、400日保持でも月$0.01に届きません。3の自動書き出しは、当面は check-app-stats スキルを月初に実行して結果を docs/ へコミットする運用で代替できます——実装ゼロで人が読める形の記録が残り、今回のような棚卸しの土台にもなります。

この集計で分かった注意点

  • 第1世代のアカウントは他アプリと共有のため、AI費用は「上限値」です。1月から5月までは当時のレポートと同じくアカウント全体の Bedrock 費用を計上しており、他の検証アプリの分が含まれている可能性があります。6月以降はタグで正確に切り分けています。
  • 1月のセッション567件には、一般公開前（1月24日から30日）の開発テストが含まれます。公開後だけで見るなら実質は2月からの数字が実力値です。
  • 依頼テーマの分類はキーワードによる機械的な振り分けです。1件を1カテゴリに寄せているため、境界にあるもの（たとえば「社内向けのAI研修資料」）はどれか一方に入っています。傾向を見る用途には足りますが、厳密な内訳ではありません。
  • 用途分析からみのるん自身の利用を完全には除けていません。除外できたのは、動作確認や自己言及とはっきり分かる122件だけです。切り分けたい場合は、提案2のユーザー識別子が必要です。
  • 共有スライドの発行数は指標化できませんでした。保存先のバケットが実質空で、共有機能の利用回数を遡って数える手段が残っていません。
  • 新環境では8月15日時点でセッションログが1件も出ていません。切替が8月14日夕方だったためで、異常ではありませんが、稼働確認は改めて必要です。
