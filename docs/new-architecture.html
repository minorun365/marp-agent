01

全体像

利用者のブラウザから 3方向へ別々につながるのが、この構成の一番の特徴です。 画面の配信、ログイン、AI の実行がそれぞれ独立していて、どれかが重くても他を巻き込みません。

02

3つの経路を分けた理由

旧構成では画面配信も AI の中継も Amplify が面倒を見ていました。新構成では役割ごとに経路を切り、 それぞれが別の理由で壊れたり詰まったりしないようにしています。

① 画面と共有スライドの配信

CloudFront が入口。既定のパスは画面配信 Lambda、/slides/ は共有スライドの S3 へ振り分けます。

Lambda は Lambda Web Adapter を挟んだ普通の Node サーバーで、同じコンテナをローカルでもそのまま起動できます。

② スライド生成エージェントの実行

ブラウザが AgentCore Runtime を直接呼びます。生成の途中経過はそのままブラウザへ流れます。

Lambda を挟まないので、Lambda の実行時間の上限が AI の生成時間の上限になりません。ここが今回の設計の肝です。

③ ログイン

Cognito が発行した合言葉（JWT）を、そのまま ② の呼び出しに添えます。エージェント基盤側がこれを検証します。

ブラウザへ AWS の一時認証情報を渡す必要がないため、旧構成にあった Identity Pool を廃止しました。

経路入口処理するもの止まったときの影響範囲
① 画面 CloudFront → Lambda React のビルド成果物、実行時の接続設定 JSON 画面が開けない。生成中の会話には影響しない
① 共有 CloudFront → S3 共有されたスライドの HTML（SNS 用のカード情報つき） 共有リンクだけが見られない
② 生成 AgentCore Runtime スライド本文の生成、Web 検索、PDF・PowerPoint への変換 生成だけが止まる。画面と共有リンクは生きている
③ ログイン Cognito 登録、ログイン、パスキー、Google 連携、既存ユーザーの移行 新規ログインが不可。ログイン済みの利用は合言葉の期限まで継続
03

スライド生成エージェントの中身

AgentCore Runtime の中で動いているのは、Marp CLI と変換ツール一式を同居させた ARM64 のコンテナです。 1つのコンテナがスライドの文章生成から PowerPoint 化まで完結させます。

層中身役割
頭脳考える部分 Strands Agents 道具の使い分けと会話の管理。直近6往復ぶんだけを残して古い会話を自動で捨て、トークン代を抑える
Bedrock の Kimi K2.5 スライド本文の生成。他モデル（Sonnet・GLM・Opus など）は設定を残したまま無効化中で、切り替えは環境変数だけで戻せる
道具エージェントが呼ぶ Web 検索 Tavily で最新情報を調べる。API キーは Secrets Manager から実行時に取得する
スライド出力 Marp 形式の Markdown を確定させ、画面のプレビューへ流す
共有リンク発行 スライドの HTML を S3 へ保存し、SNS 用のカード情報を埋め込む
URL 取得 指定されたページの中身を読み込んで題材にする
変換コンテナ同梱 Marp CLI ＋ Chromium Markdown から PDF と PowerPoint を書き出す。日本語フォントも同梱している
LibreOffice Impress あとから編集できる形式の PowerPoint を作る

会話履歴は同じセッション ID で呼ぶ間だけコンテナの中に残ります（目安として無操作15分・最長8時間）。 外部のメモリ基盤や DynamoDB は初期構成に入れず、必要になった時点で足す判断にしています。

04

インフラの6スタック

更新頻度で分けています。ほとんど変わらない土台と、毎回のデプロイで動く部分を混ぜないことで、 本番デプロイの影響範囲を小さく保っています。

スタック主なリソース消えると困る度
Foundation専用サブドメインのゾーン、ACM 証明書、秘密情報2本、月次の予算通知高（秘密情報は保持設定）
AuthAccess認証系 Lambda の実行ロールとログ低
AuthCognito ユーザープール、アプリクライアント、移行・Google 連携・IdP 管理の Lambda最高（削除保護つき）
WorkloadAccessエージェントと画面配信 Lambda の実行ロール、Web のログ低
Agentコンテナイメージ、AgentCore Runtime、モデル設定中（作り直せる）
Web画面配信 Lambda、Function URL、CloudFront、共有スライド S3、DNS レコード高（S3 は保持設定）
05

Amplify から置き換えたもの

Amplify が裏で引き受けていた仕事を、どこへ移したかの対応表です。 旧 が Amplify Gen2 時代、新 が今の構成です。

役割旧（Amplify Gen2）新（CDK ＋ CDKD）
画面の配信 Amplify Hosting が丸ごと担当 CloudFront ＋ 画面配信 Lambda。将来サーバー側処理を足せる余地を残した
接続設定の受け渡し amplify_outputs.json をビルド時に焼き込む Lambda が実行時に JSON で返す。同じビルド成果物をローカルと本番で共用できる
ログイン基盤 Amplify Auth が Cognito を自動生成 CDK の Auth スタックで明示的に定義。パスキーと Google を追加した
開発環境 ブランチごとの sandbox を都度デプロイ 常設の開発用 AWS 環境を持たず、手元でエージェント基盤と配信経路を再現して起動する
デプロイの起点 GitHub へ push すると自動でデプロイ push とデプロイを分離し、依頼を受けたときにスキルから手動で実行する
独自ドメイン Amplify の画面で設定 個人アカウントの親ドメインから専用サブドメインへ委任し、証明書ごと CDK で管理
秘密情報 Amplify の環境変数 公開してよい設定は CDK、鍵は Secrets Manager へ完全に分離
ブラウザの AWS 権限 Identity Pool で一時認証情報を発行 廃止。必要なのは Cognito の合言葉だけなので作らない

デプロイの入口は4つに整理済み。 手元では「画面だけ」「認証画面だけ」「エージェントも動かす」「配信経路まで丸ごと」を選んで起動し、 本番は差分確認 → 試し打ち → 完全待機デプロイ → 状態確認の順で進めます。切り戻し用のコマンドも用意済みです。

06

移行中のいま注意する点

実装を読んで見つかった、設計文書と現状のズレと、切り替え運用の要点です。

通信方式はまだ従来のまま

設計では AgentCore の標準イベント形式（AG-UI）へ移す方針ですが、現時点の実装は従来の独自ストリーミングのままです。

受け皿の設定項目だけは先に用意してあるので、切り替えは画面側とエージェント側を別々に進められます。

本番の中身は main ではない

移行期間中の本番は再構築用のブランチ側です。バグ修正を main へ入れただけでは本番に反映されません。

旧環境の CI が無いぶん、テーマの CSS はデプロイ用コマンドが配ります。手動で叩くときは配布を先に実行します。

ドメイン切り替えは段階制御

本番ドメインを新 CloudFront へ付けるかどうかは、設定値ひとつで切り替わります。切り替え前は予備のドメインだけで動かします。

旧環境の完全一致設定が優先される仕組みを使い、切り替え中に見えなくなる時間を作らない設計です。

既存ユーザーは自分では何もしなくてよい形。 これまでと同じメールアドレスとパスワードで最初にログインした時点で、裏側の Lambda が旧アカウントへ問い合わせて自動で引っ越します。 ただし Google やパスキーで先にログインした場合はこの仕組みが動かないため、初回だけはパスワードで入ってもらう必要があります。
