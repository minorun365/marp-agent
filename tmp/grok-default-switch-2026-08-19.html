01

検索が止まっていた原因

本番のログにキーの読み込み本数を出すようにして、切り分けられました。結論として、フォールバックの前に「切り替える先が無かった」のが実態です。

場所キーの本数状態
本番（修正前）1本そのキーが上限超過。切り替え先が無い
手元の .env3本1本目は上限超過、2本目と3本目は使える
本番（修正後）3本手元と同じ3本へ差し替え、検索が復旧

Tavilyのキーはアカウントごとに月1,000回の枠を持っていて、今回はキー1のアカウントが1002/1000で超過していました。本番の Secrets Manager は8月13日から更新されておらず、その1本だけを持ったままでした。

キーを差し替えても、動いているコンテナには届かない作りでした。キーは起動時に1度だけ読む実装だったので、シークレットを更新しても再デプロイするまで反映されません。全キーが使えなくなったときにシークレットを読み直すようにしたので、次からは差し替えるだけで戻ります（読み直しは60秒に1回まで）。

02

フォールバックの不具合も見つかった

切り替え先が無かったのが今回の直接原因ですが、切り替えの仕組み自体にも、キーが2本以上あっても止まる不具合がありました。同時に直しています。

BEFORE — 例外の文字列で判定していた

except Exception as e:
    error_str = str(e).lower()
    if "rate limit" in error_str or "429" in error_str
       or "quota" in error_str or "usage limit" in error_str:
        continue
    return f"検索エラー: {str(e)}"

TavilyのSDKは、応答の形によってはメッセージが空の例外を投げます。空だとどの語にも当たらず、1本目で打ち切って残りのキーを試しませんでした。

AFTER — 例外の型で判定する

except KEY_LEVEL_ERRORS as e:
    # UsageLimitExceeded / Forbidden / InvalidAPIKey
    print(f"[WARN] Tavilyキー{key_number}が使えません…")
    continue

枯渇・停止・無効はどれも「このキーの問題」なので、メッセージに関係なく次のキーへ進みます。どのキーが何で落ちたかもログに残るようにしました。

修正前のコードに対してテストを流すと、空メッセージの3ケースと全枯渇の判定が落ちます（4件失敗）。修正後は159件すべて通ります。

03

数十秒の無音の正体

最後の検索からスライドが出るまでの空白は、本番のイベントを時刻つきで記録して測りました。78秒ありました。

時刻届いたもの画面の見え方
13.7秒6回目の検索「Web検索中...」
27〜89秒10秒ごとの生存確認だけ何も変わらない（生存確認は画面に出ない条件だった）
91.7秒スライド出力の開始「スライドを作成中」
105.8秒スライド完成プレビューに反映

Grokはツールの引数を分割せず、スライド全文を書き終えてから一度に渡します。そのため「作成中」の通知が最後まで来ません。Kimiは引数を分割して送るので早い段階で通知が出ており、ここがモデル間の体感差になっていました。直した点は2つです。

  • 10秒黙ったら「スライドを作成中」を先に出す。Tipsも回るので、待ち時間が読めるようになりました。依頼の直後の考え込みと区別するため、一度なにか届いたあとに限定しています
  • 推論の深さを下げた。深く考えさせる利点が測定できなかったため low にしました。品質は下の表のとおり同等以上で、時間と費用が大きく下がります
お題推論の深さ所要はみ出し・構造違反本文量費用
KAGのみのるんmedium117秒0 / 02,179字31円
KAGのみのるんlow32秒0 / 02,353字15円
Claude CodeとCodexの比較medium171秒0 / 12,175字36円
Claude CodeとCodexの比較low56秒0 / 02,791字21円

費用は1ドル155円の参考換算。本番での実測は、検索ありの生成が106秒→63秒になりました。

04

語りかける調子の原因

ご指摘のとおり、Kimi向けのチューニングが残っていました。ただし残っていた場所はシステムプロンプトではなく、output_slide ツールの説明文でした。これは毎回モデルへ渡るので、システムプロンプトを削っても効き続けます。

BEFORE — ツールの説明文に残っていた型

- 見出し【重要】: `##` は、そのページの結論を
  述語で言い切った1文にする
- リード文【重要】: 見出しの直下に、結論を支える
  1行を必ず置く
- 表現パターン【重要】: A〜Eをローテーションする
  A. 主張+根拠型 / B. 小見出し型 / C. テーブル型
  D. 因果型 / E. まとめ型

Kimiが素っ気ない箇条書きになるのを防ぐために足したものです。Grokは元から資料調で書けるので、これが「語りかけ」に化けていました。

AFTER — Marpの表示に要るものだけ

- 見出しの階層【重要】: `#` は表紙と中タイトルだけ。
  通常スライドは `##`、小見出しは `###`
- 表: ヘッダー行の直後に区切り行を必ず置く
- 1スライド9行が上限（このツールが自動検証）
- 裏表紙・参考文献・中タイトルのクラス指定

説明文は1,947字→1,307字、システムプロンプトは1,409字→968字になりました。

スライドの見え方がどう変わったか

BEFORE — 型あり

## AgentCoreはエージェントの本番基盤をまとめて渡す

インフラを自分で組まずに、実行・権限・監視まで揃えられる

- 任意のフレームワークと基盤モデルで動かせる
- ツールとデータへ、権限付きでアクションを起こせる

見出しが動詞で言い切る文になり、その下に必ず説明文が入ります。全ページが同じ形になるため、読者へ語りかけ続ける調子になります。

AFTER — 型なし

## いま学ぶ理由

- プロトタイプのエージェントを本番へ載せるのが難しい
- インフラ、認証、ツール接続、監視を自前で揃えがち
- AgentCoreはフルマネージドでその層を肩代わりする
- 枠組みやモデルを問わず、サービス単位で組み合わせられる

見出しが項目名に戻り、説明文の押し付けも消えました。ページごとに形が変わるようになっています。

お題「KAGのみのるん」言い切り見出し「である」句点で終わる箇条書き
型あり（8月19日の本番）8 / 108件26 / 31
型あり＋日本語の指示10 / 130件0 / 46
型なし（今回）0 / 120件0 / 16

途中の段階では「である調を使わない」「句点で終わらせない」という指示で対症療法をしていました。型そのものを外したので、その指示も不要になり削除しています。

表紙とヘッダー階層

表紙は依頼の題をそのまま主題に置く形へ直しました（「AgentCoreの最新機能は本番運用向けに揃った」→「Amazon Bedrock AgentCore 入門」）。また、型を外した直後は本文スライドの見出しが # になり、テーマがタイトル用の大きさで描いてしまう崩れが出ました。これは表示に直結するので、見出しの階層だけ規則として戻しています。

途中のセリフは止めていません。「前置き・計画を文章で出さない」という抑制を外し、「何をしているかを短く言いながら進めるのは構わない」と書き換えました。止めるのは「作りますか」「この構成でよいですか」の確認質問だけです。

06

判断していただきたい点

復旧はしていますが、残量に余裕がありません。

  • 検索の残量が約1,900回です。キー2が45/1000、キー3が33/1000で、キー1のアカウントは今月分を使い切っています。1回のスライド作成で4〜6回使うので、300〜400回ぶんの作成で尽きます
  • 私の検証でも枠を使っています。今日の検証で30回ほど生成しており、そのぶんキー1の枠を消費しました。以後は検証の回数を絞ります
  • キーを増やすか有料プランへ上げるかは、みのるんの判断をお願いします。キーを足す場合は Secrets Manager の pawapo/tavily-api-keys をカンマ区切りで更新するだけで、再デプロイは不要になりました

本番のシークレットを更新しました。手元の .env にある3本を反映しています。ひとつ前の版は Secrets Manager に残っているので、戻すことはできます。

調査データ：本番の生イベントを時刻つきで6本記録、モデル比較を8本、キーの残量はTavilyの利用状況APIで確認。
