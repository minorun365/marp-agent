01

何が起きていたか

前回はハーネス（バックエンド）とAPIレベルの検査だけで済ませ、画面と日本語の質を見ていませんでした。ご指摘の2点は原因が別々で、うち1つはこちらが足した指示が直接の犯人でした。

日本語の硬さこちらの指示が原因

「箇条書きは句点で終わる1文にする」という指示を、Kimi向けのプロンプトからそのまま持ち込んでいました。Grokはこれを真面目に守り、全項目を「〜である。」で締める文体になっていました。

ステータスの繰り返し重複ではなかった

本番の生イベントを取ったところ、通知はすべて別クエリの本物の検索でした。完了すると全部「Web検索完了」の一言に潰れるため、同じ行が積み上がって見えていました。

検証の穴再発防止

画面を一度も見ずに完了と報告していました。今回はブラウザで実際に送信して確認し、モックも本番同様に複数回検索するよう直しています。

02

日本語をSonnetと比べる

お題「KAGのみのるん」で、Sonnet（シンプルなプロンプト）とGrok（前回の本番プロンプト）を並べました。同じ内容を書いているのに、読後感がまったく違います。

BEFORE — 前回の本番プロンプトのGrok

## みのるんはKAGから現場知見を外へ届ける人である
本名と所属を先に押さえると、以降の肩書が追いやすくなる。
- 本名は**御田稔**で、通称はみのるんである。
- 所属はKDDIアジャイル開発センターである。
- 肩書はテックエバンジェリストである。
- クラウドと生成AIの内製開発を外へ出す。

「である」が4行続き、事実を言い換えただけの項目が並びます。リード文も資料の読み方の説明になっています。

AFTER — 今回のプロンプトのGrok

## みのるんはKAGで技術を外へ届ける人
KAGのテックエバンジェリストとして外へ技術を届ける
- 本名は**御田 稔**、発信名はみのるん
- 所属はKDDIアジャイル開発センター
- KDDI株式会社のシニアエキスパートも兼務
- クラウドと生成AIの内製開発に従事
- メンバーの登壇やブログも後押しする

句点も「である」も消え、項目が増えて情報量も上がりました。Sonnetの書き方に近づいています。

参考：Sonnetは元からこの書き方だった

Sonnet 4.6（シンプルなプロンプト）

- 2019年：KDDI情報システム本部に入社、業務システムのAWS移行を経験
- 2023年：KDDIアジャイル開発センター（KAG）へ出向
- 現職：クラウド・生成AI領域の開発・プリセールス・技術コンサルティング

句点なし、名詞句で止める、年号と固有名詞をそのまま残す。この3つが自然さの正体でした。

プロンプトへ足した指示

- 「である」調を使わない。「〜である」「〜からである」を
  見出し・リード文・箇条書きのどこにも書かない
- 箇条書きは句点（。）で終わらせない。
  名詞句で止めるか、短い言い切りで終える
- リード文は結論を支える事実を1行で書く。
  「先に押さえると分かりやすい」のような
  資料の読み方の説明を書かない
- 年号・数字・固有名詞・書名は一般化せずそのまま残す

03

検索ステータスの正体

「1回の検索で3回ステータスが出る」に見えていた件は、本番の生イベントを取って数えました。結論として通知は重複しておらず、6回の検索がそれぞれ1回ずつ通知されていました。

BEFORE — 画面での見え方

✓ Web検索完了
✓ Web検索完了
✓ Web検索完了
（テキスト）
✓ Web検索完了
✓ Web検索完了
⟳ Web検索中... "御田稔 AWS AI Hero KAG 著書"

完了した瞬間に検索語が消えるため、6本の別々の検索が同じ通知の繰り返しに見えていました。

AFTER — 何を調べ終えたかを残す

✓ Web検索完了 "KAGのみのるん 概要"
✓ Web検索完了 "KAGのみのるん 最新 事例"
✓ Web検索完了 "KAGのみのるん 公式 ドキュメント"
✓ Web検索完了 "KAGのみのるん 導入 判断"
✓ スライドを確認しました
✓ スライドを作成しました

ブラウザで実際に送信して確認した表示です。進んでいることが読み取れるようになりました。

あわせて2つ直しました。ひとつは検索回数で、「論点を分けて4回までを目安、足りないときだけ6回まで」と上限を下げ、1回の検索に10秒前後かかることをプロンプトへ明記しています。もうひとつは、ツールの引数が分割して届いたときに同じ検索が複数行へ割れる経路で、こちらは以前 http_request で直したのと同じ「同じ行を書き換える」形へ揃えました。

04

対象の取り違え

日本語を直した版で、別の問題が出ました。検索回数を絞った結果、Grokが「KAGのみのるん」の KAG を Knowledge Augmented Generation（別の技術）と解釈し、まったく違うスライドを作りました。

BEFORE — 検索を絞った直後

# 知識で生成を縛るKAG
## Knowledge Augmented Generationの仕組みと使いどころ

## KAGは文書検索ではなく知識で答えを組み立てる
- **Knowledge Augmented Generation**の略
- 知識グラフの構造とLLMの言語能力をつなぐ

最初の検索結果に引きずられ、「みのるん」を拾わないまま構成へ進んでいます。

AFTER — 取り違えを止める指示を追加

- 検索結果が依頼とかみ合わない（略語が別の製品を
  指している、同名の別人が出てくる等）ときは、
  対象を絞る語を足して調べ直す。
  回数の目安より、対象の取り違えを防ぐほうを優先する。
  依頼文の語をすべて拾えているか確かめてから構成に入る

同じお題で2回続けて正しく御田さんの資料になりました。本番でも「KAG みのるん」から入って人物へ寄せています。

回数を減らす調整は、単独では品質を下げます。検索は待ち時間の主因なので減らしたいのですが、減らすほど最初の解釈に固定されます。今回は「取り違えを疑ったときだけ回数を超えてよい」と優先順位を明記する形で両立させました。

06

検証のやり方を直した

同じ見落としが起きないよう、確認の手順そのものを変えました。

  • 画面を実際に動かす。認証を挟まない npm run dev:ui で送信まで通し、ステータスの見え方をスクリーンショットで確認する
  • モックを本番の挙動に合わせる。これまで検索は1回しか流れず、複数回検索したときの積み上がりをローカルで再現できなかった。4回検索するよう直した
  • 生イベントを数える。本番へ直接リクエストを投げ、通知の件数とクエリを機械で数える。画面の印象で判断しない
  • 日本語を数える。「である」の件数と、句点で終わる箇条書きの割合を毎回数える。表現の善し悪しを感覚で語らない
  • ステータスの重複はテストで固定した。同じ検索の途中経過で行が増えないこと、別の検索なら行が分かれることを、それぞれテストにしている
